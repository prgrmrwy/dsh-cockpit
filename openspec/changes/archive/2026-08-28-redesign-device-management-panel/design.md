## Context

见 `proposal.md` 的动机。本 change 修改现有 `cockpit-device-shell` 的设备管理行为契约，且实现横跨 Web 面板、共享设备事实、服务端更新逻辑、测试和仓库前馈，因此需要先固定交互与数据边界。

当前 `DevicePanel` 只渲染纵向添加表单与简单列表，Web 已能调用 `PUT /api/devices/:deviceId` 更新名称、SSH 别名、端口和启用状态，但 `DeviceStatusFacts` 不包含 SSH 别名和远端端口，前端无法可靠预填编辑表单。注册表已有持久化 `order`，状态列表也按它排序，但更新协议尚不能移动设备。

主题以 `app.css` 的深色默认令牌和 `prefers-color-scheme: light` 覆盖为唯一颜色来源。设备连接与远端工作台的架构边界保持不变。

## Goals / Non-Goals

**Goals:**

- 在一个面板内形成清晰的“总览 → 设备列表 → 添加/编辑”信息层级。
- 用同一套表单状态模型支持添加与编辑，保证失败时输入和当前持久化状态边界清楚。
- 以单次原子更新完成一台设备的移动，并沿用注册表原子写入。
- 让布局和控件在宽屏、窄屏、键盘操作及深浅主题下都可用。
- 将 OpenSpec 路由从软偏好加强为源码需求开始前的明确门禁。

**Non-Goals:**

- 不改变 SSH 验证、隧道、重连、删除确认或最小诊断语义。
- 不增加拖拽排序；本次优先提供明确、可键盘操作的上移/下移控件。
- 不新增图标库、表单库、CSS 框架或运行时依赖。
- 不重做设备总览、顶栏或设置面板的视觉体系。
- 不增加设备搜索、筛选、批量操作或高级诊断。

## Decisions

### 1. 使用响应式双栏控制台，而不是卡片网格或继续单栏堆叠

面板内部增加受控最大宽度的内容容器：标题区提供说明和摘要；主体宽屏采用“可伸缩设备列表 + 固定宽度表单”网格，窄屏通过媒体查询变为单栏。设备仍使用高密度横向管理行，操作在窄屏下换行。

选择该方案是因为设备管理属于高频控制台任务，列表更适合比较状态和顺序，双栏又能避免添加表单挤占首屏。卡片网格视觉更强但降低同屏密度；保留单栏改动最小但不能解决空间利用和层级问题。

### 2. 添加与编辑共用表单结构，但状态互相隔离

`DevicePanel` 维护明确的 `mode: add | edit` 与当前草稿。点击编辑时从设备事实构造草稿，标题、说明和提交文案随模式变化；取消编辑恢复空的添加表单。请求失败只更新当前表单的错误状态，不重置草稿；成功后才重置并刷新设备事实。

共用结构能避免两套字段校验和可访问性标记漂移。把编辑做成行内多输入会让管理行过高、窄屏难用，且容易把列表浏览与编辑状态混在一起，因此不采用。

### 3. 将可编辑连接配置纳入本机认证后的设备事实

为 `DeviceStatusFacts` 增加 `sshAlias?` 与 `remoteDshPort`，由现有受 HttpOnly cookie 保护、仅监听回环的设备列表接口返回。它们来自驾驶舱自己的注册表，不包含密码、私钥、passphrase 或 provider token。这样 SSE 更新和初始列表使用同一真相源，编辑表单无需新增详情请求或额外加载状态。

替代方案是增加单设备详情 API，但当前数据量小、字段不敏感且管理列表已经获取所有设备事实；额外端点只会增加状态同步路径。

### 4. 通过 `UpdateDeviceRequest.order` 表达移动目标，并在服务端原子归一化

共享更新类型增加可选 `order`。服务端接收目标索引后，在当前已排序记录中移出目标设备、插入边界收敛后的目标位置，再把所有记录的 `order` 归一化为连续索引，最后执行一次注册表保存并更新受影响 lifecycle 的记录。Web 的上移/下移只发送目标设备的新索引。

相比连续发送两台设备的 order 更新，这避免中间重复序号和第二次请求失败造成部分排序。相比新增批量 reorder 端点，它复用现有更新资源并满足当前单步移动需求。

### 5. 状态文案与操作语义显式映射，视觉颜色只走令牌

设备状态在管理面板显示人类可读中文标签，同时保留官方连接状态枚举作为数据属性和辅助信息依据；异常诊断仅在有值时展示。按钮使用明确文本和 `aria-label`，关闭按钮不只依赖“✕”字符。危险删除保持独立视觉层级。

CSS 新增的表面、强调、柔和状态背景或阴影值必须进入 `:root`，并在浅色媒体查询中提供对应覆盖。已有写死色若被本 change 触及，也改为令牌；不把主题值写入 JSX 内联样式。

### 6. 顶栏选中设备使用无边框选中态

移除 `.topbar-device.active` 的 border 强调，只保留主题令牌驱动的背景与前景色变化。tab 默认仍保留透明占位边框或采用等价的无布局跳变方案，确保选中切换时尺寸不发生变化；焦点可见性由独立的 `:focus-visible` 样式保证，不能以移除选中边框为由移除键盘焦点提示。

这比继续使用边框更轻量，也避免浅色主题下选中项形成厚重的胶囊描边。完全取消选中视觉反馈不可取，因为仍需明确当前工作台归属。

### 7. 用结构/行为测试覆盖面板，用现有全仓命令做回归

新增 `DevicePanel` 测试，覆盖空状态、设备事实呈现、添加失败保留输入、编辑预填及失败保留、启停、删除确认、上移/下移请求和可访问名称。服务端测试覆盖 order 边界、连续归一化、原子持久化以及 SSH 别名编辑失败不改变记录。样式测试只断言关键响应式选择器和主题令牌约束，不绑定像素级快照。

视觉最终通过现有 `127.0.0.1:3090` 刷新进行黑盒检查，不启动替代应用服务器。

### 8. 在仓库前馈中增加 OpenSpec 路由硬门禁

修改 `CLAUDE.md`（`AGENTS.md` 的符号链接目标），在“前馈要点”中前置规则：任何可能修改源码的需求先检查活跃 change；UI、布局、交互、响应式、可访问性、主题与文案语义都属于用户可观察行为；`bounded`、单文件或纯 CSS 不是跳过理由。仅恢复现有 spec 的明显 bug、无外部行为重构、纯测试或纯文档可不新建 change，且回复中必须说明适用例外。

同时明确仓库规则优先于通用 skill 的轻量流程，proposal 阶段与 apply 阶段不得合并。这里只修改项目级前馈，不创建或改写通用技能。

## Risks / Trade-offs

- **[设备事实新增配置字段扩大响应体]** → 字段体积很小，只在本机认证接口中返回，并明确禁止任何凭据字段进入事实类型。
- **[编辑连接字段会触发生命周期变化，用户可能短暂看到重连]** → 沿用现有 `updateRecord` 行为和诊断呈现；保存按钮显示进行中状态，失败不提交持久化记录。
- **[移动一台设备需要更新所有记录的连续 order]** → 在一次内存变换和一次原子 registry save 中完成；设备规模小，复杂度可忽略。
- **[双栏在中等宽度下拥挤]** → 以内容最小宽度而非设备类型判断断点，操作区允许换行，低于断点统一单栏。
- **[测试过度绑定 DOM/CSS 会阻碍后续视觉迭代]** → 测试用户可观察语义、请求负载和关键响应式/令牌不变量，不做完整 DOM 或像素快照。
- **[强化前馈仍是文本约束，无法机械保证每次遵守]** → 使用 MUST、可观察触发条件和必须执行的 `openspec list --json` 预检，减少“改动小”解释空间；后续可另行考虑 CI 校验，但不在本 change 范围。

## Deferred Follow-ups

### 全局设备 tab 前后切换快捷键

用户希望使用 `⌘⌥←` / `⌘⌥→` 切换当前 active 设备 tab 的上一个/下一个。该能力不纳入本 change 的 spec 与 tasks，后续应以独立 OpenSpec change 评估和实施，原因如下：

- 该组合键与 macOS 浏览器的标签页导航存在冲突，浏览器可能先于页面消费事件，不能直接承诺可靠性。
- 工作台焦点通常位于不同 loopback 端口的跨源 iframe，子页面中的键盘事件不会冒泡到驾驶舱壳。
- 可选 `dsh-cockpit-bridge` 可以在 iframe 内监听后向 parent 发送受来源校验的 `postMessage`，但标准 DSH 设备不保证安装 bridge，核心快捷键不能静默依赖它。
- 后续 change 需明确：无冲突键位与跨平台映射、仅壳焦点还是 bridge 渐进增强、输入框/编辑器/终端焦点下的抑制规则、首尾停止或循环，以及浏览器与 PWA standalone 的验收差异。

当前推荐保留“切换相邻设备并在首尾循环”的产品语义，但在验证浏览器可用键位之前不锁定 `⌘⌥←` / `⌘⌥→`。

## Migration Plan

1. 先更新共享类型和服务端事实/排序更新，保持新增字段和 `order` 均向后兼容。
2. 再更新 Web 面板和样式；旧设备注册表无需迁移，已有 `order` 会在首次排序操作时归一化。
3. 更新项目级 OpenSpec 前馈及测试，运行 build、typecheck、test、lint。
4. 构建 Web 产物后刷新现有 `http://127.0.0.1:3090/` 验证深浅主题、宽窄布局及主要管理流程。
5. 如需回滚，可回退 Web 呈现；共享响应中的新增字段和更新请求中的可选字段不影响旧客户端。若同时回退服务端，则 Web 也应一并回退，避免发送未支持的 `order`。
